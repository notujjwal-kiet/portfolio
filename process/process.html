process — how it gets built

Build, test,
iterate.

I don't trust a plan I haven't broken. The workflow below is the one that has survived contact with real projects — it's less about discipline and more about not lying to myself about progress.
01

Understand the problem

Read the spec, then read it again. Ask the person who wrote it what they actually need. The gap between those two answers is where projects die.

02

Prototype the smallest version

No polish, no assets, no edge cases. One feature that proves the concept. If the prototype is boring to use, the finished product will be worse.

03

Test on real hardware

My laptop is not the target device. The ESP32 dev board is not the production board. Test on what the user will actually hold, ideally before telling anyone it's done.

04

Ship incrementally

A version that works today beats a version that's perfect next month. Version numbers are a promise to the user that the thing will keep getting better.

05

Write it down

If I can't explain how it works in one paragraph, I don't understand it yet. Documentation is the test I run on myself.
